# AFD DP6TP4 与 EP16 Prefill 性能演进报告

日期：2026-09-04

## 1. 摘要

本报告整理 DeepSeek-V4-Flash prefill 场景下，AFD DP6TP4 与 EP16 的四阶段性能演进。报告仅使用以下口径：

- AFD：DP6TP4、FFN EP8、32 张 A3 NPU，`max_num_batched_tokens=65536`（MBT=64K）。
- 单 EP16：DP4TP4/EP16、16 张 A3 NPU，MBT=8K。
- 双 EP16：两个独立的 DP4TP4/EP16 实例，共 32 张 A3 NPU，MBT=8K，由 least-load router 分流。
- 负载点统一为系统级 offered RPS 4/6/8。

实验演进如下：

1. AFD 尚未包含 `ffb9e2f` DP 调度修复时，与单个 EP16 比较。为对齐 32 卡规模，将单 EP16 的 RPS 2/3/4 吞吐乘 2，映射为系统 RPS 4/6/8；TTFT 不做缩放。
2. AFD 加入 `ffb9e2f` 后，继续与上述“双 EP16 估算值”比较。
3. 为消除线性外推的不确定性，实际部署两个 EP16，并通过 least-load router 压测。
4. AFD 侧进一步包含共享专家相关修复后，与双 EP16 router 的实测结果比较。

主要结论：

- `ffb9e2f` 的主要收益是显著降低 TTFT，而非低负载吞吐：相对修复前 AFD，RPS 4/6/8 的 P95 TTFT 分别下降 23.4%/35.0%/44.7%，P99 分别下降 21.5%/32.5%/39.7%；RPS 8 吞吐提高 8.3%。
- 单 EP16 乘 2 的估算在低负载尚能描述吞吐，但不能可靠描述多实例路由、实例间波动和尾延迟；实际双 EP16 的结果验证了重新实测的必要性。
- 最终 AFD 与实际双 EP16 相比，在 RPS 4/6/8 的吞吐分别高 1.2%/0.6%/3.8%，所有列出的 TTFT 统计量均更低。
- 最终 AFD 的优势在 RPS 4 最明显：Mean/P50/P95/P99 TTFT 分别低 21.3%/18.3%/23.5%/24.3%；RPS 6、8 的优势较温和。

## 2. 数据与计算口径

所有纳入结果满足：

- 模型：`dsv4`。
- 数据集 SHA-256：`1ebccbd149bc8f28568d3d5eced3911d2a9473fb015bdb829b898a26abf63d08`。
- 每个 repeat 包含 1,536 个请求，输出长度为 1 token。
- 每轮输入 token 总数均为 15,803,063；`max_concurrency=None`、`burstiness=1.0`。
- Prefix cache 和 KV connector 均关闭。
- 47 份 `result.json`，共 72,192 个成功请求，0 个失败请求。
- 表中吞吐和 TTFT 是同一配置下各 repeat 的算术平均；TTFT 分位点是 benchmark 每轮所报告分位点的跨轮平均。
- `Token/s` 使用 `total_token_throughput`。由于每请求只生成 1 token，该值基本反映输入 token 吞吐。

单 EP16 的“×2 估算”规则：

- RPS 2/3/4 分别映射到系统 RPS 4/6/8。
- `request_throughput` 和 `total_token_throughput` 乘 2。
- Mean、P25、P50、P90、P95、P99 TTFT 保持单实例实测值，不乘 2。
- 该估算隐含两个实例性能一致、请求完美均分且 router 无开销，因此只作为阶段 1、2 的历史比较口径。

## 9. 结论与建议

按实验演进，可以形成以下判断：

1. 修复前 AFD 的主要问题不是低负载容量，而是 DP 调度造成的 TTFT 和尾延迟恶化；在 RPS 8 还出现明显吞吐损失。
2. `ffb9e2f` 基本消除了这一问题，使 AFD 在系统 RPS 4/6/8 上达到与 EP16×2 估算相当或更好的水平。
3. 双 EP16 router 实测说明线性外推并非完全错误，但它会遗漏 router 行为、实例间不均衡和尾延迟，因此正式结论应优先使用双 EP16 实测，而不是 EP16×2 估算。
4. 在版本更一致、样本更充分的最终比较中，AFD DP6TP4 在吞吐和全部 TTFT 分位点上都领先双 EP16；当前数据支持“AFD 性能整体优于双 EP16”的结论，但领先幅度随负载而变化。
5. 若后续需要将结果用于正式发布或 PR 性能声明，建议在完全相同的 vLLM/vLLM Ascend/plugin commit、同一机器对和交替运行顺序下，再做一次 A/B/A 或 B/A/B 测试，以排除版本与节点漂移。
